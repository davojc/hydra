# Hydra — Design Spec

**Date:** 2026-10-03
**Status:** Approved in brainstorming, pending written-spec review
**User guide (design preview):** https://claude.ai/artifact/RcSjybbshNoCCvRabb2zTf

## 1. Purpose

Hydra runs terminals inside named **environments**. An environment bundles identities — Claude account, GitHub account, git author and SSH key, cloud CLI logins, other AI CLI accounts, arbitrary secrets — and applies them to every process started in that terminal.

It is a personal tool with two goals:

- **A. Stop identity mix-ups.** No more pushing with the wrong GitHub account or burning the wrong Claude subscription.
- **B. Parallel agents on different accounts.** Run several Claude Code sessions side by side, each signed in to a different account, to split usage limits and billing.

### Success criteria

1. `hydra shell <env>` opens a PowerShell or Git Bash shell in which `claude`, `gh`, `git`, `ssh`, `aws`, `az`, `gcloud`, `gws`, `kubectl` and `codex` all use that environment's identity, with no manual switching.
2. Two terminals in different environments can run Claude Code at the same time on different accounts without affecting each other's logins.
3. A `git push` or `gh` write command from a folder bound to a different environment is blocked, whether typed by the user or run by Claude Code.
4. All environments share one Claude setup (skills, plugins, settings, CLAUDE.md), with per-environment overrides.
5. `hydra whoami` shows, per provider, the identity actually in use and whether it matches the environment.

## 2. Scope

**v1 (this spec):** Windows 11, PowerShell 7 and Git Bash; a Rust core library plus `hydra` CLI; Windows Terminal integration; providers listed in §5.

**Later (interfaces must allow, not built now):** macOS and Linux (secret store and shell launch implementations); a custom Tauri terminal app built on `hydra-core`.

**Out of scope:** automatic environment switching on `cd`; WSL; sharing environment definitions with a team; reimplementing Warp features (blocks, AI input).

## 3. Concepts

- **Environment** — a named profile (`work`, `personal`, `client-acme`) with a label, a colour, provider configs, and optional folder bindings.
- **Provider** — one compiled-in module per identity type. Implements:
  - `materialise(env, ctx)` — creates/refreshes its files under `~/.hydra/state/<env>/`.
  - `contribute(env, ctx) -> Contribution` — environment variables, PATH prepends, and secret references for the child process.
  - `check(env, ctx) -> IdentityReport` — the identity actually active (for `whoami`/`doctor`).
  - optional `auth(env, ctx)` — runs the tool's login flow inside the environment.
- **Secret store** — trait with a Windows Credential Manager implementation (`keyring` crate). Config holds only references: `secret:<env>/<key>`. Values never touch disk or logs.
- **Binding** — maps a folder to an environment, via config glob rules or a `.hydra` file in the folder.
- **Guard** — shims for `git` and `gh` that check write operations against bindings and allowed owners.

## 4. Architecture

### 4.1 Workspace layout

```
hydra/
  crates/
    hydra-core/       # config, env model, provider trait, resolution, bindings, merge — no I/O to OS-specific APIs
    hydra-providers/  # claude, github, git, aws, azure, gcloud, gws, kube, codex, gemini, env
    hydra-platform/   # SecretStore + ShellLauncher traits; windows impl now
    hydra-cli/        # `hydra` binary; also the shim entry point (argv[0] dispatch)
```

Later: `hydra-app` (Tauri) depends on `hydra-core`, `hydra-providers`, `hydra-platform`.

### 4.2 On-disk layout

```
~/.hydra/                       # overridable with HYDRA_HOME (used by tests)
  config.toml                   # global: bindings, default shell, guard settings
  envs/<env>/                   # USER-EDITED, one folder per environment
    env.toml                    # label, colour, provider sections
    claude/                     # optional Claude overrides: settings.json, CLAUDE.md, skills/ …
  base/claude/                  # shared Claude layer (from `hydra import claude`)
  state/<env>/                  # GENERATED by hydra; safe to delete, rebuilt on next launch
    claude/                     # CLAUDE_CONFIG_DIR (private Claude state lives here too)
    gh/  git/gitconfig  aws/  azure/  gcloud/  gws/  kube/  codex/
    shell/                      # generated pwsh profile + bash rcfile
  shims/                        # git.exe, gh.exe (copies of hydra.exe)
```

The split is by who edits a file: everything the user writes is under `config.toml`, `envs/` and `base/`, which can go in a dotfiles repo. Everything under `state/` and `shims/` is hydra's. The exception is that `state/<env>/claude/`, `gh/`, `gcloud/` etc. also hold logins and history written by the tools themselves, so "safe to delete" means "costs a re-login", and `hydra` never deletes `state/` on its own.

An environment's name is its folder name under `envs/`. `hydra env new <name>` creates `envs/<name>/env.toml` from a template; `hydra env rm <name>` deletes `envs/<name>/` and, after confirmation, `state/<name>/`, and removes the environment's secrets from the secret store.

### 4.3 Launch flow (`hydra shell work`)

1. Load and validate `config.toml` and `envs/<env>/env.toml`.
2. For each configured provider: `materialise`, then `contribute`.
3. Merge contributions. Two providers setting the same variable is an error naming both.
4. Resolve `secret:` references from the secret store.
5. Add `HYDRA_ENV=<env>`, `HYDRA_HOME`, and prepend `~/.hydra/shims` to `PATH`.
6. Generate the shell init file (prompt snippet) and launch:
   - pwsh: `pwsh -NoLogo -NoExit -Command ". '<state/work/shell/init.ps1>'"` (the init file dot-sources the user's `$PROFILE` first).
   - bash: `bash --rcfile <state/work/shell/init.bash> -i` (the rcfile sources `~/.bashrc` first).
7. Any failure in steps 1–5 aborts the launch (fail closed, §8).

`hydra run <env> -- <cmd>` does steps 1–5 then spawns `<cmd>` directly and returns its exit code.

## 5. Providers

| Section | Mechanism |
|---|---|
| `claude` | `CLAUDE_CONFIG_DIR=state/<env>/claude`. Layered from `base/claude` (§6). |
| `github` | `GH_CONFIG_DIR=state/<env>/gh`, plus `GH_TOKEN` from secret `<env>/github-token`. `hydra auth github <env>` (alias `gh`) runs `gh auth login` in the env, then reads the token (`gh auth token`) into hydra's store. `owners` / `strict` feed the guard. |
| `git` | Generates `state/<env>/git/gitconfig`, sets `GIT_CONFIG_GLOBAL` to it. File contents: `[include] path = ~/.gitconfig`, then `user.name`, `user.email`, optional `user.signingkey` + `gpg.format = ssh`, `core.sshCommand = ssh -i <key> -o IdentitiesOnly=yes`, and `credential.https://github.com.helper = !gh auth git-credential` (with an empty helper line first to reset inherited helpers). |
| `aws` | `AWS_PROFILE`; optional `isolate = true` adds per-env `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE`. |
| `azure` | `AZURE_CONFIG_DIR=state/<env>/azure`. |
| `gcloud` | `CLOUDSDK_CONFIG=state/<env>/gcloud`. |
| `gws` | `GOOGLE_WORKSPACE_CLI_CONFIG_DIR=state/<env>/gws`. Alternative mode `credentials = "secret:<env>/gws-creds"` writes the credentials JSON to a per-env file at launch and sets `GOOGLE_WORKSPACE_CLI_CREDENTIALS_FILE`. |
| `kube` | `KUBECONFIG=state/<env>/kube/config` (or a configured path). |
| `codex` | `CODEX_HOME=state/<env>/codex`. |
| `gemini` | `GEMINI_API_KEY` from a secret. |
| `env` | Arbitrary variables; values are literals or `secret:` references. |

`whoami` groups `gcloud` and `gws` under one `google` line when both are configured.

### 5.1 Config example

`~/.hydra/envs/work/env.toml`:

```toml
label = "acme work"
color = "#1f9a8a"

[git]
name    = "David"
email   = "work@example.com"
ssh_key = "~/.ssh/id_ed25519_work"

[github]
owners = ["acme"]
strict = true

[aws]
profile = "acme-dev"

[gcloud]
[gws]

[env]
LINEAR_API_KEY = "secret:work/linear"
```

`~/.hydra/envs/personal/env.toml`:

```toml
label = "personal"
color = "#c98a1e"

[claude]
mcp.exclude = ["acme*"]
```

`~/.hydra/config.toml`:

```toml
default_shell = "pwsh"

[bindings]
"E:/acme/**" = "work"
"E:/AI/**"    = "personal"
```

Bindings stay global: resolution needs every rule in one place, overlapping rules are easy to spot, and the guard reads one file per call instead of every environment's. Loading validates that every binding names an existing environment.

Only configured providers are active; an unconfigured provider's variables are left unset — and actively removed if inherited from the parent process (e.g. a stray `AWS_PROFILE`), so an environment never leaks another's identity.

## 6. Claude layering

`base/claude/` is the shared layer. At each launch, the claude provider builds `state/<env>/claude/`:

- **Linked (directory junctions, no admin needed):** `skills/`, `agents/`, `commands/`, `plugins/` → `base/claude/<same>`, unless `envs/<env>/claude/<same>/` exists, in which case that directory is linked instead.
- **Merged (regenerated each launch, header comment marks them generated):**
  - `settings.json` = deep-merge(base `settings.json`, `envs/<env>/claude/settings.json`). Objects merge recursively; arrays and scalars from the override replace.
  - `CLAUDE.md` = base `CLAUDE.md` + `\n\n` + `envs/<env>/claude/CLAUDE.md`.
  - MCP servers: servers in the merged config whose names match any `mcp.exclude` glob are removed.
- **Private (never touched by hydra after creation):** credentials, `.claude.json`, history, `projects/`, memory, todos, and anything else Claude writes.

`hydra import claude` copies `~/.claude` (excluding credentials, history, projects, and other private state) into `base/claude/`. It never moves or deletes the original. Absolute paths inside plugin metadata (e.g. `plugins/installed_plugins.json`, `known_marketplaces.json`) are rewritten from the old location to `base/claude/` during import.

## 7. Bindings and guards

### 7.1 Binding resolution

For a working directory, collect candidates: the nearest ancestor `.hydra` file (`env = "<name>"`) and every matching `[bindings]` glob. The most specific wins: a `.hydra` file beats a glob at the same or shallower depth; among globs, the longest literal prefix wins. No match means unbound (guards pass).

### 7.2 Shims

`hydra wt install` and `hydra init` copy `hydra.exe` to `shims/git.exe` and `shims/gh.exe`. On start, the binary inspects its own file stem: `hydra` runs the CLI; `git`/`gh` run the guard.

Guard steps:

1. Find the real binary: search `PATH` with the shims directory removed. Cache the result in `shims/.resolved` keyed by PATH hash.
2. If `HYDRA_ENV` is unset or `HYDRA_ALLOW=1`, pass through.
3. Classify the command. Guarded: `git push`, `git commit`; `gh pr create|merge|edit|close|comment`, `gh repo create|delete|edit|fork`, `gh release create|delete|edit`, `gh issue create|edit|close|comment`, `gh api` with `-X`/`--method` other than GET. Everything else passes through.
4. Wrong environment: if the cwd binds to an environment other than `HYDRA_ENV` → **block** (exit 1, message naming both environments and the fixes).
5. Wrong owner (git push / gh repo commands only): if the env has `github.owners`, resolve the target remote's owner (`git remote get-url <remote>`, parse GitHub HTTPS/SSH URLs). Owner not in list → **warn** to stderr and continue, or **block** when `strict = true`.
6. Run the real binary with the same args, inheriting stdio; forward Ctrl-C (console control handler that ignores the signal in the shim so the child receives it); exit with the child's code.

Override: `hydra allow -- <cmd...>` runs the command with `HYDRA_ALLOW=1` set for that child only. In Git Bash, `HYDRA_ALLOW=1 git push` also works.

Guard latency budget: < 15 ms added per invocation on a warm cache.

## 8. Error handling

- **Fail closed on launch.** If any provider fails to materialise or contribute, or a secret is missing, `hydra shell`/`hydra run` exit non-zero listing every failing provider with a suggested fix. No partial environments.
- **Fail open in the guard.** Internal guard errors (unreadable config, malformed binding) print `hydra: warning: …` and pass through. Only a positive wrong-environment or strict-owner decision blocks.
- **Generated files are disposable.** Merged Claude files, gitconfig, shell init, and the WT fragment are rewritten each time; each carries a "generated by hydra — edit X instead" header.
- **Secrets.** Never written to disk except where a tool requires a file (gws credentials mode), in which case the file lives under `state/<env>/` with the user-only ACL and is rewritten each launch. `doctor`/`whoami` show only presence and the last four characters.
- **Import safety.** `hydra import claude` refuses to overwrite a non-empty `base/claude/` without `--force`.

## 9. CLI surface

```
hydra init
hydra import claude [--force]
hydra env new|list|edit|rm <name>
hydra shell <env> [--shell pwsh|bash] [--cwd DIR]
hydra run <env> -- <cmd...>
hydra auth <provider> <env>
hydra secret set|rm <env>/<key>        # value read from a hidden prompt
hydra bind <path> <env>
hydra allow -- <cmd...>
hydra whoami
hydra doctor [<env>]
hydra wt install
```

### 9.1 Windows Terminal integration

`hydra wt install` writes `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\hydra\hydra.json` with one profile per environment × shell (`"<env> · pwsh"`, `"<env> · bash"`), each with `tabColor` set to the env colour and `commandline` set to `hydra shell <env> --shell <shell>`.

### 9.2 Prompt

The generated init files prefix the prompt with `[<env>]` in the environment colour (24-bit ANSI). `HYDRA_ENV` and `HYDRA_ENV_COLOR` are exported for Starship / oh-my-posh users.

## 10. Testing

- **Unit (`hydra-core`):** config parsing and validation errors; binding resolution precedence; contribution merge and conflict detection; settings deep-merge; MCP exclude globs; CLAUDE.md concatenation; GitHub remote URL parsing; guard command classification.
- **Provider tests:** each provider materialises into a temp `HYDRA_HOME`; assert files and contributed variables. Snapshot tests (`insta`) for generated gitconfig, merged settings.json, shell init files, and the WT fragment.
- **Integration (Windows CI, GitHub Actions `windows-latest`):** build binaries; create an env; run the shimmed `git` against a local bare repo in bound and unbound folders; assert block, warn, strict-block, `hydra allow`, and exit-code passthrough. Secret store tests use a `hydra-test/` namespace and clean up.
- **Runtime self-check:** `hydra doctor` compares actual identities (`gh api user`, `git config user.email`, Claude account, `aws sts get-caller-identity`, `gcloud config get account`, gws auth status) with expectations.

## 11. Assumptions to verify early in implementation

Each is checked by a small spike before the dependent provider is built; if one fails, the listed fallback is used.

1. **Claude Code stores credentials inside `CLAUDE_CONFIG_DIR` on Windows** (not a shared Credential Manager entry). Fallback: per-env `ANTHROPIC_API_KEY`/OAuth token via secret, documented limitation.
2. **gh with `GH_CONFIG_DIR` + `GH_TOKEN`** keeps accounts fully separate. (`GH_TOKEN` takes precedence, so this is expected to hold.)
3. **gws keyring entry** (encryption key for stored credentials) is either per-config-dir or harmless when shared. Fallback: gws credentials-file mode (§5).
4. **Claude Code follows directory junctions** for `skills/`, `plugins/`, etc., and tolerates generated `settings.json`. Fallback: copy instead of link, re-synced on launch.
5. **Plugin metadata path rewriting** on import is sufficient for plugins to load from `base/claude/plugins`. Fallback: per-env plugin install with a shared marketplace cache.
6. **Claude Code on Windows resolves `git`/`gh` through the inherited `PATH`** so shims intercept its commands.
